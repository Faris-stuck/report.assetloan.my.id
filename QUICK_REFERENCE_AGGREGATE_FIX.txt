QUICK REFERENCE - AGGREGATE DATA FIX
================================================================================

THE PROBLEM IN ONE SENTENCE:
Modal showed "Belum Dikembalikan" even though items were already returned
because the system only read the latest return submission, not the aggregate.

================================================================================
WHAT WAS FIXED (3 THINGS)
================================================================================

1. /api/user/get-detail.php
   BEFORE: Read only latest pengembalian record
   AFTER:  Aggregates (sums) returns across ALL pengembalian records
   RESULT: Modal shows correct total items returned

2. /api/peminjaman/get_detail.php
   BEFORE: Counted only returns with status='Selesai'
   AFTER:  Counts ALL return submissions regardless of status
   RESULT: Return form shows correct remaining items

3. /api/peminjaman/return.php
   BEFORE: Allowed return submission for completed borrowings
   AFTER:  Blocks submission if all items already returned
   RESULT: Users cannot submit duplicate returns

DATABASE QUERY CHANGES SUMMARY
================================================================================

OLD QUERY (BAD):
  SELECT id FROM pengembalian WHERE peminjaman_id = ? 
  ORDER BY id DESC LIMIT 1  ← Only one!

NEW QUERY (GOOD):
  SELECT barang_id, SUM(jumlah_kembali)
  FROM detail_pengembalian
  WHERE pengembalian_id IN (
    SELECT id FROM pengembalian WHERE peminjaman_id = ?
  )
  GROUP BY barang_id  ← All items, grouped!

EFFECT: Correctly totals returns across multiple submissions

STATUS VALUES CHEATSHEET

- Sebagian Dikembalikan → User can submit more ✓
- Proses Return         → User can submit more ✓
- Dikembalikan          → LOCKED - No more submits ✗
- Sebagian Rusak        → LOCKED - No more submits ✗
- Semua Rusak           → LOCKED - No more submits ✗
- Selesai               → LOCKED - No more submits ✗

FINAL STATUSES (Cannot submit return):
Dikembalikan, Sebagian Rusak, Semua Rusak, Ditolak, Selesai

BEFORE & AFTER EXAMPLE
================================================================================

SCENARIO: User borrows 5 laptops, returns in 2 batches

BEFORE FIX:
┌─ Batch 1: User returns 3 laptops
│  Modal shows: 3/5 returned (partial) ✓
│  DB actual: 3 returned
├─ Batch 2: User returns 2 laptops  
│  System only reads Batch 2!
│  Modal shows: 2/5 returned (WRONG) ← Bug!
│  DB actual: 3 + 2 = 5 returned
│
└─ Result: User sees "Sebagian Dikembalikan" instead of "Dikembalikan"

AFTER FIX:
┌─ Batch 1: User returns 3 laptops
│  Modal shows: 3/5 returned (partial) ✓
│  DB actual: 3 returned
├─ Batch 2: User returns 2 laptops
│  System reads both Batch 1 + 2!
│  Modal shows: 5/5 returned (CORRECT) ✓
│  DB actual: 3 + 2 = 5 returned
│
└─ Result: User sees "Dikembalikan" matching header ✓

================================================================================
QUESTIONS ANSWERED
================================================================================

Q: Will this break existing data?
A: No. Query changes don't affect data, only how it's read.

Q: Do I need to migrate data?
A: No. No schema changes, no data structure changes.

Q: What if a user is in the middle of returning items?
A: System works fine. Counts all submitted so far, shows remaining.

Q: Can users see old incorrect status?
A: Only if they have cached API response. Clear cache after deploy.

Q: What if pengembalian status is not 'Selesai'?
A: System still counts it in aggregate. Status='Selesai' is just one state.

Q: Is this a security change?
A: No. Only how existing data is aggregated, no new permissions/access.
