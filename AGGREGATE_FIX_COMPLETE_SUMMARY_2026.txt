================================================================================
WHAT WAS THE PROBLEM?
================================================================================

SCREENSHOT EVIDENCE:
- User reported modal header showing "Dikembalikan" but detail items showing "Belum Dikembalikan"
- Same borrowing, same items, inconsistent status display
- This confused users and made the system appear broken

ROOT CAUSE FOUND:
- System creates separate pengembalian records for each return submission batch
- When user returns items in multiple submissions (e.g., 3 items first, 2 items later):
  * First submission creates pengembalian_id = 18
  * Second submission creates pengembalian_id = 19
  * APIs only read from LATEST (pengembalian_id = 19)
  * Missed returns from earlier submissions (pengembalian_id = 18)
  * Result: Aggregate calculation incorrect

EXAMPLE:
- Peminjaman: 5 items of Laptop
- User Action: Submit return 3 items → pengembalian #1 created
- System Read: 3/5 items returned (CORRECT)
- User Action: Submit return 2 items → pengembalian #2 created
- System Read: Only from pengembalian #2 = 2 items (WRONG)
- Modal Shows: 2/5 returned (Sebagian Dikembalikan) - INCORRECT!
- Should Show: 5/5 returned (Dikembalikan) - CORRECT

================================================================================
WHAT WAS THE SOLUTION?
================================================================================

THREE API FILES FIXED:

1. /api/user/get-detail.php
   - Purpose: Provides data shown in modal popup
   - Issue: Only read latest pengembalian record
   - Fix: Changed to GROUP BY barang_id and SUM across all pengembalian
   - Test: Now aggregates 18 + 19 = 5 items total

2. /api/peminjaman/get_detail.php  
   - Purpose: Provides form data for "submit return" page
   - Issue: Only counted returns with status='Selesai', ignored pending
   - Fix: Removed the status filter, counts ALL submissions
   - Test: Now counts Diajukan, Dicek, Sebagian Dikembalikan, etc.

3. /api/peminjaman/return.php
   - Purpose: Validates and creates new return submission
   - Issue: Allowed submissions for already-completed returns
   - Fix: Added three-level validation blocking final statuses
   - Test: Prevents duplicate submissions for completed returns

TECHNICAL DETAILS
================================================================================

FIX #1: GET-DETAIL.PHP AGGREGATE QUERY
=======================================================================
BEFORE (BUGGY):
  SELECT id FROM pengembalian WHERE peminjaman_id = ? 
  ORDER BY id DESC LIMIT 1  ← Only one record!
  Then fetch detail_pengembalian from that single pengembalian_id

AFTER (FIXED):
  SELECT 
    barang_id,
    SUM(jumlah_kembali) as total_kembali,      ← Sum across ALL
    SUM(jumlah_rusak) as total_rusak,          ← Sum across ALL
    MAX(kondisi_kembali) as kondisi_kembali
  FROM detail_pengembalian
  WHERE pengembalian_id IN (
    SELECT id FROM pengembalian WHERE peminjaman_id = ?  ← ALL records
  )
  GROUP BY barang_id  ← Group by item

Result: Modal gets accurate aggregate data from database

=======================================================================

FIX #2: GET_DETAIL.PHP STATUS FILTER REMOVAL  
=======================================================================
BEFORE (BUGGY):
  LEFT JOIN detail_pengembalian dr ON ...
    AND dr.pengembalian_id IN (
      SELECT id FROM pengembalian 
      WHERE peminjaman_id = ? 
      AND status = 'Selesai'  ← Only completed submissions!
    )

AFTER (FIXED):
  LEFT JOIN detail_pengembalian dr ON ...
    AND dr.pengembalian_id IN (
      SELECT id FROM pengembalian 
      WHERE peminjaman_id = ?  ← ALL submissions!
    )

Result: Return form shows all pending returns, correct counts

=======================================================================

FIX #3: RETURN.PHP THREE-LEVEL VALIDATION
=======================================================================
LEVEL 1 - Block Final Statuses:
  $finalStatuses = ['Dikembalikan', 'Sebagian Rusak', 'Semua Rusak', 'Ditolak', 'Selesai'];
  if (in_array($p['status'], $finalStatuses, true)) {
    ERROR: "Pengembalian tidak bisa diajukan lagi..."
  }

LEVEL 2 - Allow Only Active States:
  $allowedStatuses = ['Sedang Dipinjam', 'Sebagian Dikembalikan', 'Proses Return'];
  if (!in_array($p['status'], $allowedStatuses, true)) {
    ERROR: "Pengembalian hanya bisa diajukan saat..."
  }

LEVEL 3 - Sanity Check for Completed Items:
  if (all items in pengembalian with status='Selesai') {
    ERROR: "Semua barang sudah dikembalikan..."
  }

Result: System prevents double/redundant submissions

pengembalian.status (return submission tracking):
  Diajukan (submitted, waiting check)
  Dicek (being inspected)
  Sebagian Dikembalikan (partial, waiting more)
  Sebagian Rusak (some broken, waiting more)
  Selesai (inspection complete)

================================================================================
FREQUENTLY ASKED QUESTIONS
================================================================================

Q: Why was only the latest pengembalian counted?
A: Original code used LIMIT 1 ORDER BY id DESC to get single record.
   Worked fine for single submissions, but broke for multiple batches.

Q: Why do we need three validation layers in return.php?
A: 1st layer: Explicit final status blocking
   2nd layer: Allowed status whitelist validation
   3rd layer: Item-level completion sanity check
   Multiple layers ensure no edge cases slip through

Q: What if pengembalian status never becomes 'Selesai'?
A: Validation still works:
   - LEVEL 1 & 2: Block if status is final (Dikembalikan, etc)
   - Admin/PIC responsibility to mark pengembalian as Selesai
   - System prevents submission if ALL items in any Selesai record

Q: Can users still see the old incorrect status?
A: Only if they have cached API response
   - Solution: Clear browser cache after deployment
   - New calls fetch from database with aggregate logic

Q: What about items returned with damage?
A: Aggregate correctly handles:
   - jumlah_rusak is SUM'd across all submissions
   - Status determination uses total_rusak vs total_items
   - Correctly shows 'Sebagian Rusak' or 'Semua Rusak'
